# Partner upload flow (v1)

Funded cleanup partners upload proof of each cleanup themselves: before and after photos, if they like up to 30 short videos before and 30 after, and the numbers. We review it in `/admin/`, set what we paid in EUR, and approve. Approved cleanups appear on the globe, get a shareable receipt link (`/r/<id>`) with a link preview for social media, and show up on the partner's public page (`/p/<slug>`).

```
partner phone ──/upload/?k=TOKEN──> POST /api/upload (each file, into R2)
                                    POST /api/submit  (numbers, status = pending)
you ──/admin/──> approve / reject ──> GET /api/events ──> globe + receipts
                                      GET /r/<id>      ──> link preview, then /#ev-<id>
                                      GET /p/<slug>    ──> partner page
                                      GET /crews       ──> the list of crews
                                      GET /missions    ──> the list of missions
you ──/admin/ APPROVED──> COMMENTS LINK ──> POST /api/admin/post-link (our post on Instagram or TikTok)
partner phone ──YOUR TIKTOK──> POST /api/tiktok ──> you ──/admin/ PARTNERS──> POST /api/admin/tiktok/decide
visitor ──receipt post──> POST /api/thanks ──> the counts (nothing about the visitor)
```

Internal folders (ops, docs, migrations) are not part of the deployed output. `scripts/build-site.sh` copies an allowlist (`index.html`, `404.html`, `_routes.json`, `site/`, `upload/`, `admin/`, `apply/`, `impressum/`, `stories/`, `data/events/`) into `dist/`, and Pages serves only `dist/`. A path that is neither a file there nor a Function answers 404 with `404.html`. Without a top-level `404.html`, Pages takes the site for a single-page app and answers 200 with the homepage, also for `/.env.cloudflare` or `/wrangler.toml`: no file leaked, but scanners report it. `/404` itself shows the page with 200 (Pages serves `404.html` there like any page), which is harmless. `functions/_middleware.js` still answers 404 for the private paths (any first path segment that starts with a dot, except `/.well-known/`, and `ops/`, `docs/`, `functions/`, `migrations/`, `scripts/`, `tests/`, `assets/`, `reports/`, `research_notes/`, `public-repo/` and the READMEs), but only as a backstop, so even a deploy of the repo folder itself would not serve `.env.cloudflare` or `.dev.vars`. Every path `_routes.json` does not exclude runs it. The zone sends Pages a normalized path ("Normalize URLs to origin", step 4, item 5), and the middleware decodes the path again before it checks, so an encoded path like `/%6fps/...` gets a 404 either way.

**Security headers.** `_headers` gives every static page `X-Frame-Options: DENY`, nosniff, `Referrer-Policy: strict-origin-when-cross-origin` and the policy `frame-ancestors 'none'; script-src 'self'; object-src 'none'; base-uri 'none'`: scripts only from this site (our files and Cloudflare's `/cdn-cgi/` email decoder), so a slip in escaping crew text could never run a script that reads the admin token. No page has an inline script or handler (the `#privacy` one-liners of `/apply/` and `/upload/` run from their own scripts). `/admin/*` also gets `default-src 'none'` with only this site's scripts, requests, pictures, media, styles and fonts (inline styles for admin.js's style attributes); browsers enforce both policies. `_headers` does not reach pages a Function builds, so they set their own: `/crews`, `/missions` and `/p/<slug>` the strict `PAGE_HEADERS` (no script at all; `/p/<slug>` adds the `PUBLIC_MEDIA_URL` host to its pictures when that is set), and `/r/<id>` and `/m/<no>` `pageHeaders` (`functions/_lib/util.js`): no framing and no script but their one redirect line, allowed by its SHA-256. If `PUBLIC_MEDIA_URL` is ever set, add its host to `img-src` and `media-src` of the `/admin/*` line in `_headers` too. Cloudflare adds `Strict-Transport-Security: max-age=15552000` (6 months, no subdomains, no preload; SSL/TLS, Edge Certificates, since 2026-11-19) to every HTTPS answer of sapu.earth, the Functions' too.

## One-time setup (owner, about 15 minutes)

Do these steps right after merging this branch into `main`. All commands run from the repo root. Use a pinned wrangler so everyone gets the same behaviour.

```sh
npx wrangler@4.149.0 login
```

### 0. Stop deploying internal files (do this first)

Today the Pages project serves the whole repo, and the internal docs (including `ops/verification.md`) can be read with an encoded URL such as `/%6fps/verification.md`. Fix:

1. Cloudflare dashboard, Workers & Pages, project **sapu-squad**, Settings, **Build**, Build configuration:

   - Root directory: leave empty (Functions are read from `functions/` at the repo root).
2. Change this only once `scripts/build-site.sh` is on `main`. If it is changed earlier, the build fails and the last good deployment stays live, nothing breaks.
3. Every old deployment keeps its own URL (`<hash>.sapu-squad.pages.dev`) and keeps serving the old files. Since 2026-11-19 a Bulk Redirect (account level, under Bulk Redirects: a list with the one entry `sapu-squad.pages.dev` to `https://sapu.earth`, 301, with Include subdomains, Subpath matching, Preserve path suffix and Preserve query string, and the rule that turns the list on) sends that address and every address under it to sapu.earth, so no old deployment or preview can be reached. ### 1. Create the D1 database

```sh
npx wrangler@4.149.0 d1 create sapu-earth
```

Copy the `database_id` it prints.

### 2. Apply the migration to the remote database

**Do not commit a root `wrangler.toml`.** On Cloudflare Pages a root `wrangler.toml` with `pages_build_output_dir` takes over the binding configuration from the dashboard and would break deploys. Use a gitignored config in `.dev/` instead:

```sh
mkdir -p .dev
cat > .dev/wrangler.toml <<'EOF'
# Local only, gitignored. Never commit a root wrangler.toml.
name = "sapu-earth-dev"
compatibility_date = "2026-10-01"

[[d1_databases]]
binding = "DB"
database_name = "sapu-earth"
database_id = "PASTE_THE_DATABASE_ID_HERE"
migrations_dir = "../migrations"

[[r2_buckets]]
binding = "MEDIA"
bucket_name = "sapu-earth-media"
EOF

npx wrangler@4.149.0 d1 migrations apply sapu-earth --remote -c .dev/wrangler.toml
```

This applies every migration in `migrations/` that has not run yet (0001 to 0005). Wrangler records what it applied, so running the command again is harmless.

### 3. Create the R2 bucket

```sh
npx wrangler@4.149.0 r2 bucket create sapu-earth-media
```

Keep this bucket private (no public r2.dev URL, no custom domain). It holds everything partners upload, including files that were never reviewed.

### 3b. Public media bucket (recommended before traffic grows)

On the Workers free plan all Functions share 100,000 requests per day. Serving every photo view and every video seek through `/media/<key>` uses that up fast. Approved files can instead be copied to a second, public bucket on its own domain, which Cloudflare caches at the edge with Range support, at no Function cost.

```sh
npx wrangler@4.149.0 r2 bucket create sapu-earth-public
```

Dashboard, R2, bucket **sapu-earth-public**, Settings, Custom Domains, connect `media.sapu.earth`. Only approved files are ever copied there (on APPROVE in `/admin/`), and they are deleted from it on REJECT or UNPUBLISH. After an urgent unpublish, also purge `https://media.sapu.earth/<key>` in Caching, Configuration, Custom Purge, because the edge may keep a copy for up to a day.

Without this bucket everything still works, approved files are then served through `/media/<key>`.

### 4. Add bindings and the admin secret in the Pages project

Cloudflare dashboard, Workers & Pages, project **sapu-squad**, Settings:

1. **Bindings**, Production environment:
   - Add, D1 database: variable name `DB`, database `sapu-earth`
   - Add, R2 bucket: variable name `MEDIA`, bucket `sapu-earth-media`
   - Optional (step 3b), add, R2 bucket: variable name `PUBLIC_MEDIA`, bucket `sapu-earth-public`
2. **Variables and Secrets**, Production environment:
   - Add, type **Secret**, name `ADMIN_TOKEN`, value: a long random string, for example from `openssl rand -base64 32`. Keep it in your password manager. Until `MEDIA_KEY` is set (next line) it also signs the short-lived links `/admin/` uses to show pending photos, so changing it invalidates those links (reload `/admin/`).
   - Add, type **Secret**, name `MEDIA_KEY`, value: another long random string from `openssl rand -base64 32`, not the same as `ADMIN_TOKEN`. It signs the short-lived media links (`/admin/`, and the crew page's link to its own waiting logo) and keys the IP hash. Without it `ADMIN_TOKEN` does both, and since a crew page receives such a link, anyone holding a crew link could test guesses of `ADMIN_TOKEN` offline: harmless for a long random token, not for a memorable one. Setting or changing it invalidates the open signed links (reload `/admin/`) and resets the per-address count of applications.
   - Optional (step 3b), add, type **Text**, name `PUBLIC_MEDIA_URL`, value `https://media.sapu.earth`
3. Leave the Preview environment without these bindings unless you want preview branches to write to the real database. Without bindings the API answers 503 and the homepage shows only what `data/events/index.json` lists, which since 2026-11-16 is nothing, so THE RECEIPTS says FIRST CLEANUP DROPS SOON. When `/api/events` fails in any other way (down, a 429 from the rate limiting rule, the day's Function quota used up), the homepage says it could not load the cleanups and shows `?` in the stats: the samples would hide real cleanups it cannot show.
4. Redeploy so the bindings take effect: Deployments, latest production deployment, "Retry deployment" (or push to `main`).
5. Rate limiting (dashboard, the sapu.earth zone, Security, Security rules, Rate limiting rules): one rule that counts, per IP, every request that runs a Function, and blocks that IP for 10 seconds above 100 requests in 10 seconds. The free plan allows one such rule with a 10 second window. Every path that `_routes.json` does not exclude runs a Function, unknown paths too (they reach the homepage through it), so the rule counts everything except the excluded static files. Its expression (Edit expression):

   ```
   not (http.request.uri.path in {"/" "/index.html"} or starts_with(http.request.uri.path, "/site/") or starts_with(http.request.uri.path, "/data/events/") or starts_with(http.request.uri.path, "/upload/") or starts_with(http.request.uri.path, "/admin/") or starts_with(http.request.uri.path, "/apply/") or starts_with(http.request.uri.path, "/impressum/") or starts_with(http.request.uri.path, "/stories/"))
   ```

   It slows a single script down. One IP gets at most about 10 Function requests a second, whichever path it hits (`/api/`, `/media/`, the share pages `/r/`, `/p/` and `/m/`, or a made-up one), so using up the daily Function quota (100,000 requests on the free plan) takes hours instead of minutes. It cannot stop a script that stays under the limit, or many IPs. sapu-squad.pages.dev does not pass through the zone's rules, which is why it redirects to sapu.earth (step 0.3): a request there reaches no Function. If the quota ever matters: serve photos from the public bucket (step 3b), or move to the Workers Paid plan, which has no daily quota. A blocked request gets Cloudflare's 429 page; the upload page and the housekeeping workflow wait and try again, and `/admin/` loads a video only when it is played, so a long list stays under the limit. A receipt post on a phone shows only the first 2 videos of a stage of more than 3 until SHOW ALL 30 BEFORE VIDEOS is pressed (Homepage, under On the pages), and loads a video's first frame only once the video has been near the screen for a quarter of a second, and one video at most every second (`lazyVideos` in `site/app.js`); the wide post loads a slide's video once the slide has shown for 300 ms, also one at most every second, and a video whose load failed there (this rule's 429) loads again when its slide shows again (`startStage`). Chrome asks 3 to 5 ranges of a phone's video, so a receipt with 60 videos never asks for them all at once, and scrolling or stepping through all of them stays near 50 requests in 10 s. Each range is a Function request of the day's 100,000 too: a visitor on a phone who reads a receipt with 30 videos before and 30 after to its end without pressing SHOW ALL loads only its first 2 of each stage (and a mission's video), about 5 to 25 of them, as many as a receipt with 2 videos before and 2 after (one with a video before and one after spends about 10); a visitor who shows both stages and goes through all 60, or steps through all of them in the wide post, spends about 60 to 250, so roughly 400 to 1,600 such visits use up a day. Since 2026-11-19 a stage on a phone shows its first 2 videos and the rest behind a tap (Marcus: "Yes, shorten them", and every original kept). Not changed (Marcus's call, if receipts with many videos get many visitors): serve approved media from the public bucket (step 3b, whose copy on APPROVE goes file by file, so try it with a big cleanup first), or move to Workers Paid.

   Set up on 2026-11-05 as "Flood guard: every path that runs a Function" (the first version that day only counted `/api/`, `/media/`, `/r/` and `/p/`), and `/stories/` joined the exclusions on 2026-11-15, right after the deploy that excludes it in `_routes.json` went live). Two things to know:

   - The rule sees the path after Cloudflare's URL normalization. The zone uses the type "Cloudflare": it decodes letters written as `%XX`, turns `\` into `/` and merges repeated slashes, so `/%73ite/x` is `/site/x` to the rule. Pages matches `_routes.json` against the path it receives, so "Normalize URLs to origin" (the zone, Rules, Settings, URL Normalization) must stay on: it sends Pages the same normalized path. Without it, `/%73ite/x` runs a Function that the rule does not count. Turned on 2026-11-06. Check: `curl -s -o /dev/null -w '%{http_code} %{content_type}' 'https://sapu.earth/%73ite/%FF'` answers `200 text/html`, like `/site/%FF` (with the setting off it answers `404 text/plain` from the middleware).
   - Order matters when the static folders change. Add a folder to the expression only once the deploy that excludes it in `_routes.json` is live: before that, its paths run a Function that the rule would not count. Take a folder out of the expression before or with the deploy that stops excluding it. A folder that is excluded in `_routes.json` but not yet in the expression only counts toward the limit, which is harmless.

## Limits and rules built in

- Photos are converted to JPEG on the phone (longest edge 2000 px, quality 0.85), which drops EXIF and GPS. The API only accepts JPEG and refuses JPEGs that still carry an Exif block, and it takes only what the page sends (`jpegLikePage` in `functions/_lib/util.js`, the rules of the logo check before the image data): before the image data only the JFIF header, a colour profile, comments, the tables and one plain frame, all within the first 64 KB, no stray byte, and the file must end with the end marker, so nothing hides before or after the picture. The image data itself is not walked, which keeps a 15 MB photo within a request's CPU time. Server limit 15 MB per photo.
- Videos: MP4, MOV or WebM, at most 95 MB and about 90 seconds each, up to 30 before the cleanup and 30 after it, 60 in all (since 2026-11-19; 1 of each before): each of the two video fields takes up to 30 (several picked at once where the phone allows, or one by one). They go up with their stage (`stage=before` or `after`, stored in `uploads.stage`), and the server refuses a 31st video of a stage or a 61st video (`LIMITS.stageVideos`, `LIMITS.cleanupVideos`; a video without a stage, from an older page, counts toward the 60). A mission with several spots takes the same, for the whole mission. A mission takes 1 to 4 photos and at most 1 video of the spot, with the same video limits. Before upload the phone removes the location and phone model from MP4 and MOV files (`upload/videoclean.js`).
- 1 to 4 before photos, 1 to 4 after photos.
- Per partner: 200 uploads and 8 GB per 24 hours, and at most 100 uploaded files that are not yet part of a sent cleanup (since 2026-11-19, so the biggest cleanup fits: at 4 spots up to 92 files, 4 × 8 photos and 60 videos, up to about 5.7 GB; 60 uploads, 1 GB and 40 before). The quota is reserved in one atomic D1 statement before a file is streamed, so parallel uploads cannot get around it. Files that fail the content check still count.
- NEW LINK and DEACTIVATE leave a crew's pending cleanups and their files as they are, until each is rejected (REJECT AND DELETE); only loose files go by themselves (below). Nothing caps how many cleanups a crew has pending, so a leaked link can park up to 8 GB a day in R2 as pending cleanups (R2's free 10 GB in about a day and a half, then about USD 0.015 per GB a month). PENDING lists them and the housekeeping note counts them; reject them all there.
- Uploaded files that are never sent with a cleanup or a mission are deleted after 48 hours (rows and R2 objects, cleaned up on that partner's next upload and by the scheduled housekeeping, a few times a day). A mission's photos and its video are not loose files: they do not count against the 100, the 48-hour cleanup skips them, and a cleanup cannot take them.
- Sending the same cleanup twice (for example when the phone lost the answer) returns the same reference instead of creating a duplicate.
- File types are checked by their first bytes, not just the name.
- Tokens: 32 random bytes, base64url, only the SHA-256 hash is stored. Admin token compared in constant time.
- `/media/<key>` only serves files of approved cleanups, the photos and video of open, funded and done missions, and the live logo of an active crew, to the public. `/admin/` gets signed links (HMAC with `MEDIA_KEY`, or `ADMIN_TOKEN` until it is set) that expire after 4 hours and are never cached; the crew page gets one for its waiting logo, for an hour.
- Crew logos: a 320 px square JPEG made on the phone, at most 150 KB, square 128 to 640 px, only the JFIF header, a colour profile, comments and the image (`logoJpegInfo`); at most 10 per crew in 24 hours, one waiting and one live per crew; a logo nobody decides on is declined and deleted after 90 days (see Crew logos).
- `?dl=` makes `/media/<key>` a download. `dl=1` saves it as `sapu-earth-<first 8 of the key>.<ext>`, as it always did. `dl=<name>` saves it as `sapu-earth-<name>.<ext>` when the name is lowercase letters, digits and dashes (at most 64); any other value gets the old name. The extension comes from the stored type. `dl` is not covered by the signature of an `/admin/` link (that is over the key and the expiry), so anyone with a link can change it, which is fine only because it changes nothing but the file name, and nothing from it but lowercase letters, digits and dashes ever reaches the header (never a quote, a line break or a slash). Public links work the same way.
- Public coordinates in `/api/events` and `/api/missions` are rounded to about 100 m. The homepage rounds them again, and its satellite map shows each one as an area of 80 m around that point, never as a pin, and zooms no closer than 6 m a screen px (Satellite map, under Homepage). `/admin/` keeps the exact point until 90 days after the cleanup was decided or the mission was done. Then the scheduled housekeeping rounds the stored point the same way and deletes the crew's private message (`functions/_lib/retention.js`, at most 100 rows per table per run). The receipt stays where it was on the globe.

"How to save this link" at the bottom shows it again. When the page is opened from the home screen icon, the link counts as saved and the card stays away.

### Limits and spam protection

- At most 3 photos, each at most 3 MB, the whole request at most 10 MB. The page re-encodes photos to JPEG (longest side 1600 px, quality 0.82), which drops Exif and GPS. The API refuses anything that is not a JPEG or still has an Exif block.
- At most 3 stored applications per IP address per 24 hours (the page says to wait a day or email hello@sapu.earth), and at most 40 open applications at a time (the page says to try again in a few days). Mobile networks put many phones behind one address, so now and then a crew can hit the first limit without having applied. Deciding applications frees both limits.
- IPv6 addresses count per /64 network, not per address. A phone or a home line gets a whole /64 and can use any address in it, so counting single addresses would not limit anything. IPv4 addresses (also when written inside IPv6, like `::ffff:1.2.3.4`) count as they are.
- The cap of 40 open applications is the real limit against floods: anyone with many addresses can still fill it. If the form keeps answering "busy" because of junk, delete the junk in `/admin/` (REJECT, then DELETE APPLICATION, no reply needed). Junk nobody deletes is gone after 90 days anyway.
- The application is stored before any photo is written to R2. A request that hits a limit, or repeats an application that was already stored, never writes a photo. If writing a photo fails, the application is removed again and the page retries.
- The form asks no head count: "How many people usually join?" went on 2026-11-17 (Marcus: 'Drop the head count'), so a crew signs up with its name, country, area, what it cleans and a WhatsApp number or an email. `POST /api/apply` ignores a `crew_size` sent by an older page, and `/admin/` shows Crew size only on the older applications that have one. A crew still says how many people work on each mission (POST A MISSION's price) and cleanup.
- Bots: a hidden "website" field and a minimum of 3 seconds between opening the page and sending. Both get a normal "thank you", but nothing is stored.
- Sending the same application twice (for example after a dropped connection) returns the same reference instead of a second application. The page keeps the typed answers as a draft on the phone until the application is sent. Switching language also translates the messages already on screen, the status line and TRY AGAIN included (the same `setMsg` as the upload page).
- WhatsApp numbers are cleaned up the same way on the page and on the server, by one block of code that is the same in `apply/apply.js` and `functions/api/apply.js` (`tests/e2e.sh` compares the two and runs both over the same numbers): spaces, dashes (also the Unicode ones phones paste), dots, brackets and invisible direction marks are removed, and a leading `00` becomes `+`. A number typed without `+` gets the calling code of the chosen country (the block knows the code of every country on the page with phones) in place of its national 0: `77 123 45 67` with Senegal chosen is `+221771234567`, `0803 123 4567` with Nigeria `+2348031234567`. Digits that already start with the code keep it only when the rest is as long as a mobile number there (`WA_LEN`; an Indian `9123456789` still gets `+91`). A national 0 right after the code is dropped (`+62 0812...` becomes `+62812...`, `+233 024...` becomes `+23324...`), except where numbers start with 0 (`KEEP0`: Italy, San Marino, the Vatican, Côte d'Ivoire, Benin, Congo, Gabon), so `07 07 12 34 56` from Côte d'Ivoire is `+2250707123456`. For a country without a calling code (the uninhabited ones) a number without `+` is refused, never given a guessed code. The page shows the number it will use, and turns that line into a warning when no country is chosen yet for a local number, when the code is not the chosen country's (a crew may use a phone from another country, so it does not stop the send), or when the number has more or fewer digits than a mobile number in the chosen country (`WA_LEN`, where we know it), for example an old 8-digit Côte d'Ivoire number.
- The rate limiting rule (step 4, item 5) counts `/api/apply` too, like every request that runs a Function.

- The IMPRESSUM page (`/impressum/`) names the same owner and contact and links here as `/apply/#privacy`, which opens the notice (one line of script under it in `apply/index.html`). The link says "Privacy notice for crew applications", because that is all the notice covers. Next to it are the notices for visitors and for crew uploads, see Privacy notices for crews and visitors.
- The notice is a promise. If any of this changes (another host, other fonts, other retention), change the text in `apply/index.html` and `apply/apply.js` (both languages) in the same change.

What the code does:

- **Photos** are private: only `/admin/` sees them, through signed links that expire after 4 hours. They are deleted from R2 once the application is decided. On approve, the photo list stays on the application until R2 has confirmed the delete. If that delete fails, the next cleanup run (below) tries again. One gap: when the 90-day expiry deletes an application and R2 then fails, its photos are only logged (with their keys) and not retried.
- **Rejected** applications (DELETE APPLICATION) are deleted at once, with their photos and logo.
- **Open** applications are deleted automatically after 90 days, with their photos and logo. No reply is sent.
- **The IP address** is never stored. Only an HMAC of it (keyed with `MEDIA_KEY`, or `ADMIN_TOKEN` until it is set, per /64 for IPv6) is kept for the rate limit, and only for about a day: the first cleanup run after 24 hours clears it, and deciding the application clears it at once. Changing that key only resets the rate limit.
- **Approved** applications keep the contact details and the answers while the partner is active. DEACTIVATE wipes the personal fields of the application (contact name, what they clean, WhatsApp, email, how they heard of us, links, any leftover photos, the IP hash). The partner row, the crew name, country and area stay, so the partner's history on the globe still makes sense: its receipts keep the crew's name alone, without its website, page, slug or logo (`/api/events` sends them only for an active crew).
- **When the cleanup runs**: at the start of every load of the applications list (opening `/admin/` is enough, it loads the count), in the background after every stored application, and in the background on every homepage visit (`GET /api/events`). Each run handles at most 50 rows. The scheduled housekeeping also runs it, a few times a day, see Scheduled housekeeping and notifications.

Requests from applicants (hello@sapu.earth):

- **See or correct**: an open application is on its card in `/admin/`, tab APPLICATIONS. For a partner, the Partners tab shows the contact, and the whole application is in the D1 console (`SELECT * FROM applications WHERE partner_id = (SELECT id FROM partners WHERE slug = 'their-slug');`). Corrections: reply with what changed, or edit the row in the D1 console.
- **Delete, or withdraw consent**, open application: REJECT, then DELETE APPLICATION.
- **Delete, or withdraw consent**, active partner: DEACTIVATE wipes the contact details and deletes the crew's logo (and ends the partnership, the upload link stops working, and their missions in review, open and funded are removed with their photos and videos, private notes and exact points). If you keep working together and they only want the application record gone, run in the D1 console `DELETE FROM applications WHERE partner_id = (SELECT id FROM partners WHERE slug = 'their-slug');`. The partner stays, only the application record and its contact details go.

## Missions

What a mission is and why: [missions.md](missions.md). In short, a crew posts a spot that needs cleaning with its price, Marcus funds it (or shows it as open, or declines it), the crew sends the cleanup for it from the same upload page, and APPROVE turns it into a receipt.

```
crew phone ──/upload/ POST A MISSION──> POST /api/upload (1 to 4 "now" photos, kind before; 1 video, optional, kind video)
                                        POST /api/mission (status = review)
you ──/admin/ MISSIONS──> PUBLISH ──> open    ──> globe, NEXT UP, /m/<no>
                        ──> FUND    ──> funded  ──> globe, NEXT UP, /m/<no>, send the advance
                        ──> DECLINE ──> removed, photos and video deleted
crew sends the cleanup for it ──> PENDING ──> APPROVE ──> done ──> receipt with a mission block, /m/<no> opens it
crew sends it with No mission ──> PENDING, Link to mission ──> APPROVE ──> done (the same)
```

### States

| Status | How it gets there | What the public sees |
|---|---|---|
| `review` | The crew posted it | Nothing. Its photos and video only open through `/admin/` signed links |
| `open` | PUBLISH | Globe pin, NEXT UP card, `/api/missions`, `/m/<no>`, its photos and video |
| `funded` | FUND (from review or open) | The same, with the EUR amount |
| `done` | APPROVE of the cleanup sent for it (or linked to it) | The receipt in `/api/events` with a `mission` block, `/m/<no>`, its photos and video |
| `removed` | See `removed_why` below | Nothing. Its photos and video are deleted, `/m/<no>` says it is no longer on the map |

`removed_why`: `declined` (DECLINE, from review or open), `cancelled` (REMOVE of an open mission, CANCEL of a funded one), `withdrawn` (the crew, while review or open), `expired` (28 days, below), `unpublished` (UNPUBLISH of its approved cleanup), `deactivated` (DEACTIVATE of the partner: missions in review, open and funded).

The row stays so its number is never given out again, but a removal wipes what is private. Whatever the reason, the same UPDATE that sets `removed` also sets `private_note`, `lat` and `lng` to NULL. The place name, the task, the dates and the money (`funded_eur`, `advance_eur`) stay as the record, and the photos and video are deleted (below).

Open and funded missions only show while their partner is active: `/api/missions` and `/m/<no>` check it too, as a second guard behind DEACTIVATE. A done mission stays with its receipt.

Every mission gets a short public number (`#12`): 1, 2, 3 and so on, never reused. Crews write it on a paper in one before photo of the cleanup.

### Endpoints

Partner, with the upload token in `?k=` like the rest:

- `POST /api/mission?k=` JSON `{client_ref, place_name, country, lat, lng, task, plan_date, crew_size, currency, price_local, crew_local, private_note, consent: true, media: [key, ...]}` creates a mission in review: 201 `{id, no}`. The crew page adds up both totals itself, to the cent: `crew_local` = `crew_size` × the pay for each person, `price_local` = `crew_local` + the other costs; the crew never types a total. The server checks only that `crew_local` is from 0 to `price_local`, so a page kept from before (with typed totals) is still taken. `media` holds 1 to 4 photos (uploaded with `kind=before`) and at most 1 video of the spot (`kind=video`, no stage), nothing else. The same `client_ref` again (the phone lost the first answer): sent unchanged it answers 200 `{id, no, repeated: true}`, unless the mission was removed meanwhile. Sent with changes while the mission is in review and was posted less than 2 hours ago (`MISSION_LIMITS.editMinutes`), the mission takes them, photos and video included, in one transaction: 200 `{id, no, repeated: true, updated: true}`, and the done screen says the mission now has the changes. The new set must still be 1 to 4 photos and at most 1 video (checked before anything is written), and the change only goes in when the mission holds no file besides the old and the new set, so two resends at the same moment with different files (a second video, a fifth photo) cannot both stay: one answers 409 code `media`. A photo or video taken out becomes a loose file again: it counts against the crew's unattached files and is deleted once it is 48 hours old, counted from its upload, by the crew's next upload or the scheduled housekeeping (a few times a day), whichever comes first. A changed resend later than that, or once Sapu Earth has acted on it (open, funded, done), and any resend once it was removed (withdrawn, declined, expired and so on), answers 409 code `client_ref`: the page takes a new `client_ref`, sends the photos again and posts it as a new mission when the crew taps TRY AGAIN. Errors are `{error, field?, code?}`: 400 for a bad field, 400 code `media` for files that are missing, another crew's or already used, and for anything but 1 to 4 before photos and at most 1 video (no photo, 5 photos, 2 videos, an after photo), 429 code `limit` at 5 missions waiting, on sapu.earth or funded.
- `POST /api/mission/withdraw?k=` `{id}`: the crew takes back a mission in review or open. Its photos and video are deleted, its private note and exact point wiped. 404 if it is not theirs, 409 once it is funded, done or removed.
- `GET /api/partner?k=` also lists the crew's missions: every one in review, open or funded, however old (so a funded mission never drops off the crew page), plus the 20 newest others (done or removed), newest first: `{id, no, place_name, plan_date, status, removed_why, funded_eur, advance_eur, share_url, country, crew_size, cleanup_sent, plan}`. `share_url` (`https://sapu.earth/m/<no>`) only for open, funded and done. `country`, `crew_size` and `cleanup_sent` (a cleanup for it is pending or approved) are for the crew page: a cleanup opened from a funded mission's card starts on its country and crew size, and a mission whose cleanup was sent offers no cleanup. `plan` is the crew's own task and price as posted, `{task, currency, price_local, crew_local}`: a mission cleanup's costs line quotes the price the receipt will show, as it adds up with the mission's `crew_size`; the cards of missions in review, open and funded show it as "The price you asked"; and POST A MISSION offers the task of the newest funded or done mission as a one-tap chip, and its pay for each person and other costs only while its crew pay splits evenly (`payOf`), never a price posted as one total. It is null once a mission is removed, so a declined price is never offered again. Never the notes, the review note or the exact point. `plan` is additive: the page from before it ignores it, and the crew page works without it (no amounts in the costs line, no task or price chip). `missions_enabled` is `true`; before migration 0004 it is `false` with `missions: []`, and the crew page then shows no mission cards and no POST A MISSION.
- `POST /api/submit?k=` takes an optional `mission_id`. It must be this crew's funded mission (else 400 code `mission`) with no cleanup for it pending or approved (else 409 code `mission`). A cleanup without a mission works as before. Sending the same cleanup again (same files, the phone lost the answer) returns the same id with `repeated: true`, also for a mission cleanup and also once the mission is done.

Before migration 0004, `POST /api/mission` answers 503 code `unavailable` (the upload page does not offer it then).

Public:

- `GET /api/missions`: open and funded missions of active partners, shape in [data/README.md](../data/README.md). `[]` before migration 0004.
- `GET /m/<no>`: the share page, made for "mission 12, link in bio". Its preview follows the mission: "Mission #12: <place>" while open, "Mission #12 is funded: <place>", then "Mission #12 done: <place>" with the receipt's numbers and after photo. While a mission is open or funded and has an MP4 video of the spot, the page also names it (`og:video`, for apps that play one); a MOV or WebM clip, and a done mission, get none. It then opens `/#m-<no>` (the mission post on the homepage) or, once done, `/#ev-<id>` (the receipt). A mission in review, removed (expired, declined, cancelled, withdrawn, unpublished, deactivated), open or funded of an inactive partner, or an unknown number gets a small page with status 404: "This mission is no longer on the map." with a link to the globe, one to the list of missions (`/missions`) and the generic Sapu Earth preview tags (noindex). It never says which case it is, so it gives nothing away about missions in review. Before migration 0004 too.
- `GET /media/<key>`: a mission's photos and video are public while it is open, funded or done, cached for 1 hour (not "immutable" like approved cleanup files, because a mission can still be removed). A video also takes Range requests, as for cleanups.
- `GET /api/events`: the receipt of the cleanup that completed a mission (the mission is done) has a `mission` block (number, link, now photos, `now_video` (the mission's video, or null), funded EUR, and what the crew asked in local money: `currency`, `price_local`, `crew_local` (the crew's pay in all, inside the price), and the mission's `crew_size`, which that pay was added up for). Every receipt's `media` also has `video_stages`, one for each of its videos: `before`, `after` or null. The videos come before, then after, then those without a stage, each stage in upload order (up to 30 before and 30 after).

Admin (`Authorization: Bearer <ADMIN_TOKEN>`):

- `GET /api/admin/missions?status=review|open|funded|done|removed` (default review): `{counts: {review, open, funded}, month_eur, missions}`. Each mission has every column except `client_ref` (for a removed one `private_note`, `lat` and `lng` are null), plus `partner_name`, `partner_slug`, `contact` (WhatsApp, email and name from the partner's application, or null), `late`, `overdue`, `pending_submission` (a cleanup for it waiting in PENDING, or null), `share_url`, `now` (signed photo links), `now_video` (the signed link of its video, or null) and `revision` (a fingerprint of the content, the photos and the video, so PUBLISH and FUND also refuse when only the video changed). It runs the expiry first, then retries photo deletes that failed (below). 503 code `migration` before migration 0004.
- `POST /api/admin/missions/decide` `{id, action, funded_eur, advance_pct, review_note, revision, video}`, action one of (with a `revision` that no longer matches, `publish` and `fund` answer 409 code `changed`, because a mission in review can still take the crew's changes for 2 hours; /admin/ then reloads the list. The check is repeated inside the UPDATE, with the same content columns and the same set of photo and video keys, so a resend that lands between the check and the change also answers 409 `changed`. `video` is the key of the video the card plays, or null: with a `revision`, `publish` and `fund` also answer 409 code `changed` when the mission has a video the card did not play, so an /admin/ tab opened before missions had videos cannot publish one unseen):
  - `publish`: review to open.
  - `fund`: review or open to funded. `funded_eur` is required, `advance_pct` is 0 to 100 (default 30). The answer has `advance_eur` and `rest_eur`.
  - `decline`: review or open to removed (declined), photos and video deleted.
  - `remove`: open to removed (cancelled), photos and video deleted.
  - `cancel`: funded to removed (cancelled), photos and video deleted. The advance stays with the crew, the review note keeps the money history.
  - Anything in the wrong state answers 409, so a double click or two open tabs cannot apply an action twice.
- `GET /api/admin/submissions`: a cleanup sent for a mission carries `mission` (number, status, `removed_why`, place, day, task, the money, the now photos and `now_video`). Each of a cleanup's videos (`media.videos`) has its `stage`: `before`, `after` or null. A cleanup without a mission carries `partner_missions`: that partner's funded missions with no pending or approved cleanup, soonest day first, for "Link to mission". A pending cleanup carries `contact` (name, WhatsApp, email and language from the crew's application) for the reply REJECT opens; null for a crew made with NEW PARTNER, on the other lists, and before migration 0003.
- `POST /api/admin/decide`: APPROVE of a cleanup with a mission marks the mission done in the same step. APPROVE also takes an optional `mission_id` for a cleanup the crew sent with No mission: only when the cleanup has no mission yet, and only for a funded mission of the same partner (400 code `mission` otherwise; 409 when another cleanup took that mission meanwhile). It is stored on the cleanup and the mission is marked done in the same batch. REJECT of a pending one leaves the mission funded, so the crew can send it again. UNPUBLISH of an approved one removes the mission (unpublished) and deletes its photos and video too.
- `POST /api/admin/partners/deactivate` also removes the partner's missions in review, open and funded (deactivated): their photos and videos are deleted, the private note and exact point wiped. The crew can no longer send a cleanup, so a funded mission would never be finished. Its money columns stay and its review note gets the line "Partner deactivated; advance EUR x stays with the crew." Done missions stay, they are receipts. The answer is `{id, active: false, missions_removed, funded_removed: [{no, advance_eur}]}`.

### Reviewing missions

- The **MISSIONS** tab shows how many wait for review in its name, "Funded this month: EUR X" (what was agreed for missions funded in the current UTC month, to hold against the monthly budget; a mission cancelled, or removed by DEACTIVATE, counts only its advance), then NEW, OPEN and FUNDED (oldest first, funded ones by their planned day).
- Each card: the photos and the video (when the crew sent one), the map link, what the crew will do, the day, crew size, the price in local money as it adds up ("IDR 3,000,000 in all: crew pay 15 × 100,000 = 1,500,000 (50%), other costs 1,500,000"), their private note. A crew pay that does not split evenly (posted as one total, like mission #2) shows with its head count ("crew pay 100,000 for 15 people (about 6,666.67 each, 3%)") and an orange note: "Check the crew pay with the crew: IDR 100,000 for 15 people is about 6,666.67 each, not the same whole amount for each person." Ask the crew before funding. PUBLISH, DELETE MISSION, REMOVE and CANCEL MISSION say "photos and video" when there is one, and so does the ready decline message (EN and ID).
- **FUND**: type the EUR amount and the advance (30% by default). The form says what the crew asks as it adds up ("They ask IDR 3,000,000 in all: crew pay 15 × 100,000 = 1,500,000, other costs 1,500,000."). The card says what to send now with Wise and what after the receipt. The card then moves to FUNDED and opens a "Tell the crew it is funded" box (paper colored, no delete step, CLOSE): a ready message (EN / ID) with the amounts in EUR in the crew's number format (EUR 37,50 in Indonesian), where the money goes (the crew's bank account or e-wallet, in local money, rupiah in Indonesian, at the exchange rate of the day it is sent, naming no payment service), the day written out (14 November 2026), or, when that day has passed, a request to pick a new one, the before photos with the paper with the mission number, counting the sacks, where the trash goes (waste bank, collector or official point, never burned, no sacks left by the water), the safety basics, what to do if they cannot go that day, and how to send the cleanup (SEND A CLEANUP FOR #12 on the mission's card, then SEND CLEANUP), with COPY MESSAGE, WhatsApp and email. Send the advance with Wise first, then the message. MESSAGE on a funded card opens it again. The message stays in EUR only, so the crew never reads its local price as the amount paid. The card's Advance line says "EUR y when funded (30%)": the site does not know whether it has gone out.
- **PUBLISH** shows the mission as open (NEXT UP) without funding it yet.
- For 2 hours after posting, a crew whose phone lost the answer can still send the mission again with changes. If that happens while a card is open, PUBLISH and FUND refuse with "The crew changed mission #12 after this list was loaded" and the list reloads, so you only ever publish or fund what you saw.
- **DECLINE** first shows a short reply in English or Bahasa Indonesia to copy (with WhatsApp and email buttons when the crew came in through an application), then DELETE MISSION removes it, deletes its photos and video and wipes its private note and exact point.
- A funded mission 3 days past its day with no cleanup in PENDING is marked **LATE** (`lateDays`), and the scheduled housekeeping counts it, so the GitHub note emails you (Scheduled housekeeping and notifications): ask the crew how it went, or agree on a new day. A cleanup that comes in takes it out of the count; if you reject that cleanup, the mission counts again until the crew sends it anew. Its day is the crew's own date, compared with the UTC date.
- A funded mission 14 days past its day with no cleanup is marked **OVERDUE** instead. Ask the crew, or CANCEL ("The advance stays with the crew."). When a cleanup for it is already waiting in PENDING, the CANCEL question says so: approving that cleanup later publishes it but does not mark the mission done.
- Open and funded cards have the `/m/<no>` link with COPY, for posts.
- In **PENDING**, a cleanup sent for a mission has a MISSION #12 badge, the mission's now photos next to its before photos (and its video, VIDEO NOW, #12, before the cleanup's videos), the task, "Asked" (the mission's price as it adds up, as on the mission card) and "Agreed: EUR x (advance EUR y)". APPROVE then says "Send the rest now" and that it counts the advance as sent, so check Wise first. A cleanup sent without a location (crews often send from home, and "Use my location now" is only for the spot itself) gets the mission's point in Lat and Lng, rounded to about 100 m (3 decimals, what the globe shows anyway), with the hint "The cleanup came without a location, so Lat and Lng are prefilled with the point of mission #12, rounded to about 100 m", so the receipt still gets its dot on the globe. The PENDING list only ever carries that rounded point, and the card rounds it again, so a mission removed later (UNPUBLISH, or a CANCEL in another tab while the card is open) leaves no exact point in the cleanup. A typed Lat or Lng stays, and a cleanup with its own point keeps it. Link to mission fills the point of the chosen mission the same way, like the EUR. While the mission is funded, "Paid to partner" starts with the agreed amount. Privacy: the deepest zoom is 6 m a screen px (`SAT_MPX`, tiles up to level 14), so a house is a pixel or two; a receipt is a green dot that never gets smaller than an area of 80 m around its point rounded to 3 decimals (`AREA_M`, it covers the whole 110 by 110 m box the true spot can be in), and turns see-through once it is that area; a mission's tag points into a dashed ring of the same size. On the map a pinch follows the fingers and the + and - buttons step 2.5 times. Zoomed in below 0.6, the page's own boxes step aside so the map has the screen: the crew link, SAMPLE DATA, the line WE PAY LOCAL CREWS TO CLEAN UP. EVERY CLEANUP GETS A PUBLIC RECEIPT. (`.pitch`), the hint line, the legend, the stats (kg, cleanups, funded), SEE THE RECEIPTS and SEE THE CREWS fade out and leave the layout (their row too, `.hero.map-gone .cues`), so BACK TO THE GLOBE drops to the bottom; the logo and the zoom buttons stay. They come back only zoomed far out again, above altitude 1.2, so a small zoom out leaves them away (`setUi`). While they are away, one finger moves the globe and the map every way: a vertical swipe anywhere on the first screen no longer scrolls the page or pulls it to refresh (`touch-action: none` on the canvas and on `.hero.map-on`); BACK TO THE GLOBE, or zooming out past 1.2, gives the page back. Until 2026-11-09 this waited for the whole map, so on a phone a vertical swipe on a map half in scrolled the page, or reloaded it at the top (Marcus noticed). Above, on the drawn globe, a vertical swipe still scrolls the page, so a phone can get past the globe to the receipts, but a pull down at the top of the homepage never reloads it (`overscroll-behavior-y: contain`): a finger there is on the globe. Flights (SEE THE SPOT, BACK TO THE GLOBE, which goes out to altitude 1.5, so the boxes come back) ease the altitude on a log scale; a hop of more than about 25 km from down on the map goes up about as high as the hop is long, across and down, with tiles two levels coarser on the way, and the landing view's tiles are asked for as it starts. Under reduced motion they jump. A view whose tiles all fail says "THE SATELLITE PICTURES DID NOT LOAD. TRY AGAIN LATER." and keeps the drawn globe. A session of zooming in, one SEE THE SPOT and back loads about 200 tiles (3 MB) on a large screen, a third of that on a phone. Change the tile year (`SAT_YEAR`) and the credit in `index.html` together.
- **Fingers on the globe** (homepage, "one finger on the globe holds the spot it touched" in `site/app.js`): a finger or a pen moves the planet the way a map is moved, on the globe and on the satellite map: the spot it touched stays under it (`spotAt` and `holdSpot` in the satellite math, which tests/e2e.sh checks in node), with nothing trailing behind, where globe.gl's own controls eased every move over about 10 frames and turned the planet about a third faster than the finger. A flick carries on at the finger's speed and slows down within about a second (`FLING_S`), timed by the clock, so it feels the same on a slow phone; a finger that stood still before letting go does not flick, and a touch, a zoom, a double tap or a flight stops a flick where it is. On the globe a swipe that starts up or down still scrolls the page (`touch-action: pan-y`): until the finger has gone 16 px mostly across (or 48 px any way) the planet follows it only across, and when the browser takes the swipe for the page the planet goes back to where it was, so it no longer tilts a few degrees first. Two fingers pinch at the speed globe.gl's pinch had (`pinchSpeed`), within its limits, toward the spot between the fingers, which stays between them, so two fingers move the planet too; the finger left after a pinch holds the planet again. A finger that comes down on a mission tag acts as on the planet (`#globe`'s `touch-action` in `site/styles.css`): a drag holds the planet, a swipe up scrolls the page and a tap still opens the mission, where before a drag that started on a tag did nothing and a pinch with a finger on one did not zoom. A mouse keeps globe.gl's eased spin.

### Limits and housekeeping

- 1 to 4 photos of the place now, through the same photo pipeline as cleanups (JPEG on the phone, no camera data), and at most 1 short video of it with the limits of a cleanup video (MP4, MOV or WebM, 90 seconds, 95 MB, location and phone model removed from MP4 and MOV). Place up to 120 characters, task up to 600, private note up to 1000.
- The planned day is from yesterday (time zones) to 120 days ahead.
- At most 5 missions per crew in review, open or funded at once.
- **Expiry**: a mission nobody funds goes away after 28 days, counted from posting while in review and from publishing while open. It is removed (expired) with its photos and video, and its private note and exact point are wiped. The job runs at the start of every `GET /api/admin/missions` (the MISSIONS tab and its count in `/admin/`) and after every `GET /api/missions` (each homepage visit), and a few times a day by the scheduled housekeeping, at most 50 missions per run. Funded missions never expire, they turn OVERDUE instead.
- Removing a mission for any reason deletes its photo and video rows first (every file of the mission, whatever its kind), then the files in R2 (and the public bucket). If R2 fails the keys are logged and not retried, but without a row `/media/` never serves them again. If deleting the rows fails, the next `GET /api/admin/missions` deletes them (and their files).
- Exact locations stay in `/admin/` while a mission is live and are wiped when it is removed; the public map is rounded to about 100 m. 90 days after a mission is done, the housekeeping deletes its private note and rounds its stored point (`functions/_lib/retention.js`).
- Not fixed on purpose: withdrawing a mission frees the upload rows of its photos and video, so the crew gets a few of its 200 daily uploads back. And the orphan cleanup deletes rows before R2 objects (a failed R2 delete leaves an unreachable file, never a broken row).

### Spots: one mission at several places and days

A mission can run at up to 4 spots, each with its own place, point and day; it stays one mission with one cleanup, one receipt and one payment (docs/missions.md, Spots; Marcus said 'Yes, build it' on 2026-11-17). Spot 1 is the mission's own place, point and day, as always. `functions/_lib/spots.js` reads and checks the list (`extraSpots`, `spotList`, `lastDay`), and `withSpots` runs every query without the new columns before migration 0008.

- **Data** (`migrations/0008_spots.sql`, three additive columns): `missions.spots`, spots 2 to 4 as `[{place_name, lat, lng, date}]`, written by Sapu Earth with an UPDATE in the D1 console for now (docs/missions.md, Adding a spot); `submissions.spots`, the same for the cleanup, copied by `POST /api/submit` with the day the crew cleaned each spot; `uploads.spot`, 2 to 4 for a cleanup's before or after photo of that spot (NULL for spot 1, every video and every older photo). The points of spots 2 to 4 are stored at 3 decimals, so they hold nothing private and need no wipe or trim.
- **`POST /api/upload?k=&kind=before|after&spot=2..4`**: a cleanup photo of that spot. 400 code `kind` for a video, a spot outside 2 to 4, and before the migration.
- **`POST /api/submit`**: for a mission with spots, 1 to 4 before and 1 to 4 after photos for each spot (by their `spot`), the videos up to 30 before and 30 after (60 in all) for the whole mission, as for any cleanup, and `spot_dates`, the day of spots 2 to 4 (YYYY-MM-DD, not in the future; `cleanup_date` is spot 1's), else 400 (code `spot_dates` for the days). The mission's spots go on the cleanup with those days. A photo of a spot the cleanup does not have is refused (400), also for a cleanup without a mission. A cleanup takes up to 92 files (8 photos a spot and 60 videos), so a crew may have 100 loose files (`LIMITS.unattached`: 100 since 2026-11-19, 40 from 2026-11-17, 30 before).
- **`GET /api/partner`**: a mission with spots carries `spots`, `[{no, place_name, date}]`, spot 1 first, never a point. The crew page asks each spot's photos (`before_2`, `after_2`, ... fields made from spot 1's) and day (`spot_date_2`, ...), names each field by its spot, hides Use my location now and sends `spot_dates` (docs/missions.md, Spots).
- **`GET /api/missions`, `GET /api/events`**: `spots` on a mission and on its receipt, and `media.before_spots`, `media.after_spots` on the receipt (data/README.md). The homepage draws a pin at each spot (`mgeo`, `geo`), SPOT rows, one SEE SPOT ON SATELLITE button per spot (`satRow`), and on a phone the first before and after of each spot (`spotPairs`).
- **`GET /m/<no>`, `/missions`**: every place in the title or the card's head, every place with its day in the preview, "days 5 and 6 Jan 2027" on the card (`fmtDays`). `/p/<slug>` and `/crews` show spot 1.
- **Admin**: `GET /api/admin/missions` and `GET /api/admin/submissions` carry `spots` (spot 1's point exact, the others rounded) and each photo's `spot`; LATE and OVERDUE, and the housekeeping's late count (`LAST_DAY_SQL`), count from the last spot's day; a mission with spots is never in `partner_missions`, and `POST /api/admin/decide` refuses to link a cleanup without a mission to one (400 code `mission`).

### On the phone

Both pages run the same block (`toLogoJpeg` and its helpers, the same text in `upload/upload.js` and `apply/apply.js`, which `tests/e2e.sh` compares and runs in node). Whatever is picked (a JPEG, a PNG, a WebP, the first frame of a GIF, HEIC where the phone opens it, an SVG) is drawn whole onto a 320 x 320 canvas, as big as fits inside a 10 px margin and centred, never cropped, so nothing of a logo or its lettering is lost and there is no crop screen. A picture under 96 px on its longest side is refused ("This picture is too small for a logo"). The background under it is white, except for a light logo on a see-through PNG (more than 2% see-through and the rest light on average), which gets the site's ink so white lettering does not vanish. The canvas becomes a JPEG at quality 0.9 (0.75 if that is over 150 KB, which a 320 px square never is in practice: usually 10 to 60 KB), and `cleanJpeg` keeps only the JFIF header, the colour profile and the image: no Exif, GPS, XMP or phone data. A file over 60 MB is refused before it is opened. Nothing about a logo is kept on the phone: no draft, no IndexedDB.

On the crew page the tile shows the crew's letters on tape yellow (`monogram`: SB for Sapu Bersih Padang) until there is a logo, "…" over it (the letters hidden behind it) while the phone prepares the square, the new square at 60% while it is sent, the waiting logo with a dashed border and the live one with a solid border. The line next to it says where it stands (waiting for Sapu Earth, which checks it and shows it once approved, shown on sapu.earth, not used and why another one is welcome, or a new one waiting while sapu.earth keeps the current one), and the button says + ADD YOUR LOGO or CHANGE LOGO. The rules sit above the button, so they are read before the pick: the crew's own logo or a close-up of it on its banner or shirt, filling the picture; no people, no phone or bank account numbers, no QR codes (Indonesian banners often carry a QRIS donation code), no other organization's logo. The send tries 4 times (after 2, 5 and 10 s, so a 10 s block of the rate limiting rule is outlasted), and a refusal or a failed send leaves the panel as it was, with the reason under it. While a logo is on its way, the picker stays locked, a language switch or a fresh list keeps the tile and the line, and the 5-minute refresh waits. GET /api/partner says whether logos are on (`logo.enabled`); before migration 0006 the panel stays hidden.

On `/apply/` the logo gets the same square, shown as a thumbnail with ✕ (a new pick replaces it), and SEND waits for it with the photos ("Preparing your pictures…"). Its hint says that if we work together, we can show it next to the crew's name, never that we will. A logo the server refuses stays in its field with "The logo was not accepted. Remove it and add it again, or send without a logo." It is never kept in the draft.

### On the server

`POST /api/logo?k=` takes the raw JPEG (`Content-Type: image/jpeg`, a `Content-Length`, at most 150 KB) and checks it with `logoJpegInfo` (`functions/_lib/logos.js`) without decoding the picture: it starts with FF D8 FF, every segment before the image data is whole, and they are only the JFIF header, a colour profile (APP2 ICC_PROFILE), comments, the tables (DQT, DHT, DRI) and exactly one plain frame header (SOF0 to SOF2, 8 bit, 1 or 3 components), square and 128 to 640 px. After the first scan the image data is skipped (a 0xFF in it is followed by 0x00, a restart marker or a fill byte), only tables, a restart interval and more scans may follow, and the first end marker (FF D9) must be the file's last two bytes: so no Exif, XMP or other block hides behind the picture, and nothing (a second picture, a camera's data, any file) is appended to it. That is exactly what `cleanJpeg` leaves of a canvas JPEG, WebKit's included; any APP1 (Exif, XMP), another APPn anywhere, another kind of JPEG, a second frame, anything after the end or a size that does not fit is refused (415 code `logo`). Since the picture is never decoded, the check is one of the file's structure: what a phone adds (camera data, an appended file) cannot pass, and anything else would have to sit inside the picture's own data. The answers: 201 `{logo}` (the crew page's logo state, below), 405 for another method, 404 for a link that is not valid, 415 code `type`, 411 and 413 and 400 code `size`, 415 code `logo`, 429 code `limit` after 10 logos in 24 hours, 503 code `migration` before migration 0006. The file is written to MEDIA first, then one batch marks the logo that waited before it as gone and inserts the new one as waiting, both only while the crew is under its daily limit, so two sends at once cannot pass it. A failed batch, or a refused insert, deletes the new file at once. The file before its row means a waiting row always has its file, so LOGOS TO CHECK never shows a broken picture and APPROVE never makes a missing file live.

`GET /api/partner` adds `logo: {enabled, live, review, declined, initials}`: `live` the public address of the live logo, `review` a signed link (1 hour) to the one waiting, `declined` true when the last logo the crew sent was not used and nothing waits (with a live logo, only when that came after it), `initials` the letters for the tile. It is additive: a crew page from before it ignores it.

`POST /api/apply` takes an optional file entry `logo` under the same checks (400 `field: logo` for two logos or an empty one, 413 over 150 KB, 415 code `logo`). Its row goes in with the application in one batch (`partner_id` NULL), and its file is written after the photos. If a file cannot be written, the files and both rows are deleted again, as for photos.

- **LOGOS TO CHECK** sits at the top of the PARTNERS tab when an active crew's logo waits, oldest first: the new logo (96 px), the crew's name, when it was sent ("sent 2026-11-14 09:12 (2 days ago)"), what sapu.earth shows now (the live logo at 40 px, or "no logo yet"), APPROVE LOGO and DECLINE. After DECLINE the crew page asks for another one, or, when the crew has a live logo, keeps showing it ("Sapu Earth could not use your new logo, so sapu.earth keeps showing this one."), and the flash says which. The tab label says how many wait, "PARTNERS · 1 LOGO", in yellow like the other counts. Approve the crew's own logo, or a close-up of it on its banner or shirt. Decline people or faces (children above all), another organization's, a sponsor's, a party's or a government's logo, phone or bank numbers, QR codes, text that asks for money, and anything you would not show on sapu.earth.
- A partner row shows its live logo (40 px, loaded lazily), "new logo waits under LOGOS TO CHECK" while one waits, and REMOVE LOGO, which asks first and takes the logo off sapu.earth for good. DEACTIVATE says the logo is deleted too.
- A decision that comes too late (the logo was decided or replaced meanwhile, in another tab or by a newer one from the crew, or its crew was deactivated) says so with "The list was reloaded." and draws the lists again. The panel, the rows and the tab label always come from one answer, and a NEW LINK box showing in a row stays through the redraw.
- **APPLICATIONS**: a card with a logo shows it (96 px, a link to the full picture) above the photos, and APPROVE AS PARTNER has a box, ticked: "Show this logo on sapu.earth." Ticked, the logo is live with the new crew at once; unticked, it is deleted and the crew can send another one from its crew page. An `/admin/` tab from before logos sends no box: the logo then waits under LOGOS TO CHECK, so nothing goes live unseen and nothing is lost. DELETE APPLICATION deletes the logo with the rest.
- Setting a logo yourself is not built: a crew does it in two taps, so the answer to a crew that asks is "Add it on your crew page, under YOUR LOGO".

### Every delete

1. A crew sends a logo while one waits: the waiting one is gone, its file deleted (`POST /api/logo`).
2. APPROVE LOGO: the crew's live logo before it is gone, file deleted.
3. DECLINE: declined, file deleted.
4. REMOVE LOGO: declined, file deleted.
5. APPROVE AND CREATE PARTNER: box unticked, declined and file deleted; file missing, gone; ticked, live; from an old tab, it waits under LOGOS TO CHECK.
6. DELETE APPLICATION: the logo is claimed first (gone, only while the application is open), so an APPROVE AND CREATE PARTNER of the same application in another tab at the same moment cannot make it live (that takes a waiting logo); then the file and the rows are deleted. If the approval came first, nothing is claimed, the live file stays and DELETE APPLICATION answers 409. A retry claims the same row again.
7. The 90-day expiry of an open application: `sweepApplicationLogos`, run inside `expireApplications`, deletes the files and then the rows of logos whose application is gone. It also catches any leftover of 6 and 10, and a claimed logo whose application was approved in that moment.
8. DEACTIVATE: live and waiting logos are gone, files deleted (`logos_removed` in the answer). The housekeeping retries one that failed.
9. The housekeeping's logo sweep (`sweepLogos`): waiting or live logos of inactive crews are gone with their files; a logo of an active crew that waited 90 days (`LOGO.reviewDays`) is declined with its file, and the crew page asks for another one; declined and gone rows older than 30 days have their keys deleted from R2 once more, then the rows.
10. A failed request: in `/api/logo` a failed batch, or a refused insert, deletes the new file at once; in `/api/apply` a failed photo or logo write claims the logo first, as in 6, then deletes every file and the rows.

Failed R2 deletes are logged with their keys. By then the row is never live, so `/media/` never serves the file publicly. Known gap: a Worker killed between the file write and the batch in `/api/logo` leaves one file of at most 150 KB with no row. ### Limits and caching

- At most 10 logos per crew in 24 hours, every status counted, checked inside the insert. 150 KB each, square 128 to 640 px. One waiting and one live per crew (unique indexes). One logo per application, inside its 10 MB form and its 3 applications per address.

## Crew TikTok accounts

A crew can have its own TikTok account linked from sapu.earth. Marcus asked on 2026-11-19 that crews can add their TikTok links. A link per cleanup already existed (Post links and thanks: a crew pastes the link to its own post with the cleanup, and the receipt links it), so this is the crew's account, one per crew, sent from its crew page (YOUR TIKTOK, TIKTOK KRU KAMU in Bahasa Indonesia, between YOUR LOGO and YOUR PUBLIC PAGE). Nothing shows on sapu.earth before Marcus approves it, as with logos and post links: an account can ask for money or show people, and a crew link can leak.

```
crew page ──YOUR TIKTOK, SEND──> POST /api/tiktok (the account waits)
you ──/admin/ PARTNERS, TIKTOK TO CHECK──> APPROVE TIKTOK ──> live: /p/<slug> and the crew's card on /crews
                                         ──> DECLINE ───────> dropped, the crew page says Sapu Earth is not showing it
you ──/admin/ PARTNERS, a partner row──> REMOVE TIKTOK ──> off sapu.earth the same way
crew page ──REMOVE──> POST /api/tiktok with no account ──> off sapu.earth at once, the waiting one too
```

### On the phone

The field takes the crew's name with its @ (`@sapu.earth`), the link to its profile (`https://www.tiktok.com/@sapu.earth`, also with `?_t=...&_r=1` as the TikTok app copies it, on www., m. or the bare host, with or without `https://`), or the link to one of its videos or photo posts, whose account it takes. A name without the @ is refused, since it could be a website (`kru.org`), and so is a short link (`vm.tiktok.com`, `vt.tiktok.com`, `tiktok.com/t/`), which redirects and names no account anybody can check: "Short links (like vt.tiktok.com) cannot be checked. Type your crew's TikTok name instead, like @sapu.earth." An account is 2 to 24 of a to z, 0 to 9, `.` and `_`, with at least one letter or digit, kept in lower case. The block that reads it (`tiktokAccount`) is the same in `upload/upload.js` and `functions/_lib/tiktok.js`, which `tests/e2e.sh` compares and runs in node on 45 values.

The line under the field shows the link as it will show ("Your TikTok: tiktok.com/@sapu.earth"), or in orange why it is not taken. SEND (or Enter) sends it. The line above the field says where the crew's account stands: none ("Add your crew's TikTok account. Once Sapu Earth has checked it, your crew's public page and the list of crews on sapu.earth link to it."), waiting, a new one waiting while sapu.earth keeps linking the live one, live, not shown ("Sapu Earth is not showing the TikTok account you sent. You can send another one, or ask us on WhatsApp why."), or a new one not used while the live one stays. REMOVE asks first and takes the live and the waiting account off at once. The rules sit under the field: only the crew's own account, no other person's or organization's, none that asks for money or shows people who did not agree to be shown, or we take the link off and tell the crew why. A send tries 4 times (after 2, 5 and 10 s), as a logo does, and a list asked for before its answer never brings the older state back. Nothing about it is kept on the phone. `GET /api/partner` says whether TikTok accounts are on (`tiktok.enabled`); before migration 0009, and with an older server, the panel stays hidden.

### On the server

`POST /api/tiktok?k=` takes `{account}` (JSON, at most 2 KB) and reads it with the same block. The answers: 200 `{tiktok}` (the crew page's state `{enabled, live, review, declined}`, as `GET /api/partner` has it), 405 for another method, 404 for a link that is not valid, 400 code `tiktok` for anything that is no account and code `short` for a short link, 413 over 2 KB, 503 code `migration` before migration 0009. An account waits in place of one that waited, and the live one stays until Marcus approves the new one; the live account sent again clears what waits; the waiting one sent again keeps its place. An empty account or null deletes the crew's row. The send is one statement that writes only while the crew is active, so a send in the moment of a DEACTIVATE leaves no row behind it.

`POST /api/admin/tiktok/decide {partner_id, account, action}` (`approve`, `decline`, `remove`) names the account Marcus saw. A crew that sent another one meanwhile, a double click or a second tab answer 409 code `state`, never a decision on an account Marcus did not see; 409 code `inactive` for a deactivated crew, 404 for an unknown one, 503 code `migration` before 0009. `GET /api/admin/partners` adds `tiktok` (the live account) and `tiktok_review` (`{account, sent_at}`) to each partner, and `counts.tiktok` (the accounts of active crews that wait).

One `crew_tiktok` row per crew (`migrations/0009_crew_tiktok.sql`): `live`, `review`, `sent_at` and `declined_at`. Only the account's name is stored, never a link, and every page builds the one link from it (`https://www.tiktok.com/@<account>`) after reading the name once more (`accountOf`), so a value written by hand in the D1 console that is no account never reaches a page. A declined account is not kept.

The line under it says "// thanked 46 times. terima kasih is thank you in indonesian. the crew sees the count on its crew page." ("// be the first to thank this crew. ..." at 0, "in malay" in Malaysia, and without the middle sentence elsewhere), then "// sending…", and "// counted. thanked 47 times so far. the crew sees the count on its crew page.", or "// today's thanks are full. try again tomorrow." (a cap or an undo stopped it; the button comes back), "// thanked 46 times. this receipt takes no more thanks." ("// this receipt takes no more thanks." at 0; 409 code `inactive`: Sapu Earth stopped working with the crew while the page was open, and the receipt stays with its count, as its post shows after a reload; the button goes), "// this receipt is no longer on sapu.earth." (404: it was unpublished; the button goes), or "// not sent. check your connection and tap again." Before migration 0007 `/api/events` has no `thanks`, so only the samples show the button.
- **Nothing on the device**: `site/app.js` uses no localStorage, sessionStorage, IndexedDB or cookie. A tap is remembered in memory (`thankedHere`) only while the page is open, which is the feature the visitor asked for (TKG 2021 § 165(3)); a mark kept across visits mainly to stop a second count is not clearly covered by that exemption. So one person can thank again after a reload: the caps bound that, and every text says times, not people.
- **Only from our pages**: `POST /api/thanks` (`functions/api/thanks.js`) takes a JSON body of at most 1 KB with a receipt id, and only from a page of this site: the Origin header must be the site's own and Sec-Fetch-Site, when the browser sends it, `same-origin` (else 403 code `origin`), and the type JSON (else 415 code `type`). An HTML form on another site cannot send JSON, and another site's script would need a CORS preflight, which gets 405 like every method but POST, with no `Access-Control-Allow-Origin`. It reads no internet address and sets no cookie, and every answer is no-store. 404 code `receipt` when the id is no approved receipt, 409 code `inactive` for a receipt of a crew no longer active (it stays on sapu.earth and takes no new thanks), 503 code `migration` before migration 0007.
- **The caps** (`THANKS` in `functions/_lib/social.js`): at most 1,000 counted thanks per receipt and 5,000 for the whole site per UTC day. A tap past a cap writes nothing and answers `counted: false`. The site cap is on `thanks_site.counted`, every thanks counted that UTC day, which neither undo nor UNPUBLISH lowers: taking thanks off never makes room for more the same day (the receipt cap needs no such count, since an undone receipt takes no more thanks that day and an unpublished one none at all). The site cap is required: D1 Free allows 100,000 rows written a day, and running out stops every query until 00:00 UTC. At the caps at most about 16,000 rows are written a day, 16% of that, whatever is taken off later.
- **One batch, one mark**: `countThanks` runs one batch (one transaction). Its first statement counts the tap in `thanks_days` (the receipt and its UTC day) only if every check passes (an approved receipt of an active crew, both caps, no undo on that receipt or that day) and writes the request's random mark there; the site's day (`thanks_site`) and the receipt's total (`thanks`) move only where that mark is, so the three counts move together or not at all, also with taps at the same moment. Each day's site count is always the sum of its standing receipt rows, and a receipt's total the sum of its days, also after UNPUBLISH and the undos (`tests/e2e.sh` checks both sums).
- **Where the counts show**: in the receipt post; on its card as THANKED 46 TIMES (only above 0, never on a sample); in the body of `/r/<id>` ("Thanked 46 times on sapu.earth."); on `/p/<slug>` ("// visitors thanked this crew 47 times on its receipts." under the numbers, and "thanked 12 times" in each receipt row); and on `/crews`, after what was paid ("thanked 47 times"). Never in tags or link previews, where a count goes stale, and not on `/missions` (not built). Nothing ranks, orders or pays crews by thanks: `/crews` stays newest activity first, and its HOW THIS LIST WORKS says thanks are applause, not votes, and never money. After a tap, the post and its card show the larger of the server's count and the loaded one at once; the other pages catch up within 5 minutes (`/api/events` 60 s, the pages 300 s).

### Every delete

1. REJECT of a pending cleanup deletes its `post_links` row (the crew's link) in the same batch.
2. UNPUBLISH deletes its `post_links` row and its `thanks` and `thanks_days` rows in the same batch (`dropReceiptSocial`), and the site's day counts lose its thanks (their `counted` stays, so no room opens under the site cap), so a receipt taken off the site keeps no link and no count.
3. DEACTIVATE takes the crew's own links off all its receipts (`dropCrewPostLinks`). Sapu Earth's links stay. Its thanks stay with its receipts, which take no new ones. If the link step fails, it is logged, the receipts already show none of the crew's links, and the housekeeping's post link sweep takes them off.
4. REMOVE (our post), REMOVE LINK and REMOVE CREW LINK clear that slot, and a row with both slots empty is deleted.
5. UNDO ON THAT RECEIPT takes that receipt's thanks of that UTC day off its total and the site's day count. Its day row stays at 0 with the number taken off, and that receipt takes no more thanks that day. The site's `counted` for that day stays, so the undo makes no room under the site cap.
6. UNDO THE WHOLE DAY takes every receipt's thanks of that day off, the same way. The site's day is kept as undone, and nobody can thank for the rest of that day.
7. A cleanup lost to a race in `/api/submit` takes its link with it.
8. The housekeeping's post link sweep (`sweepCrewPostLinks`) takes the crew's own links off the receipts of inactive crews.

Nothing else is stored: no title, no count and no picture of a post, nothing about who reads, comments or taps.

### Reports of illegal content (DSA)

Crew uploads make sapu.earth a host under the EU Digital Services Act, so `/impressum/` has a Report illegal content paragraph right after the contact: "Think something on sapu.earth is illegal? Email hello@sapu.earth with the link to it and why you think it is illegal, and say that what you write is true as far as you know. You may add your name, but you do not have to. We confirm that your report arrived and tell you what we decided. How we handle your email is in the privacy notice below. This address is also our contact point for authorities and users under the EU Digital Services Act. Crews can also write to us in their WhatsApp chat with Sapu Earth. We answer in English or German." Marcus confirmed the last sentence on 2026-11-11. The visitor notice's Emails and reports line says how these emails, and reports a crew sends in its WhatsApp chat, are handled and kept. The routine follows Art. 11, 12, 16, 17, 18 and 53:

1. **Confirm** that the report arrived (Art. 16(4)), with the ready answer below.
2. **Decide** whether the content is illegal or breaks our rules.
3. **Take it down** if so: UNPUBLISH (a cleanup), REMOVE LOGO, REMOVE TIKTOK (a crew's TikTok account), REMOVE CREW LINK or REMOVE (a post link), or by hand for one file (its `uploads` row and R2 object). A crew's website (on `/p/<slug>` and its receipts) has no button: clear it by hand in the D1 console with `UPDATE partners SET url = NULL WHERE slug = '<slug>';`. ### Scheduled housekeeping and notifications

Cloudflare Pages has no timer, so GitHub runs one. `.github/workflows/housekeeping.yml` calls `POST https://sapu.earth/api/housekeeping` on a schedule of every 3 hours (at minute 17 past 0, 3, 6 and so on, UTC). GitHub starts scheduled runs late and skips many of them: in the first two days (6 to 8 November 2026) it ran in 7 of 17 slots, 20 minutes to almost 3 hours late, so the runs came 5 to 10 hours apart. To run it now: GitHub, the repo, Actions, Housekeeping, Run workflow.

One run does what otherwise only happens when someone uses the site, one batch per job, with the same code:

- the 28-day mission expiry, then the retry for photos a mission removal left behind,
- the application retention: the 90-day expiry, old IP hashes, leftover photos of decided applications,
- loose uploads older than 48 hours, of every crew, 50 per run, oldest first. Before, only a crew's own next upload removed its loose files, so the files of a crew that never uploads again (or was deactivated) stayed.
- the logo sweep (`sweepLogos`): the waiting and live logos of inactive crews, a logo of an active crew that waited 90 days for a decision (declined and deleted, so the crew page asks for another one; only the housekeeping runs this), and declined and gone records older than 30 days, 90 rows per step,
- the post link sweep (`sweepCrewPostLinks`): the links to their own posts on the receipts of inactive crews, after a DEACTIVATE whose link step failed (our own post links stay); before migration 0007 it finds no table and logs nothing,
- the TikTok sweep (`sweepCrewTiktok`): the TikTok rows of inactive crews, after a DEACTIVATE whose TikTok step failed; before migration 0009 it finds no table and logs nothing,
- the 90-day trim: 90 days after a cleanup was decided or a mission was done, the crew's private message goes and the exact point is rounded to about 100 m, 100 rows per table per run. Only the housekeeping runs it, so if the workflow stops, so does the trim.

So even with no visitors, an expired mission or application goes at the next run, usually within a few hours. A job that fails is logged and the others still run.

The endpoint is public and needs no token, because every job only removes what is due anyway. It does the work at most once per 10 minutes per Cloudflare data center (a mark in the Cache API); any other call only reads the counts and answers `"ran": false`. The answer is `{"ran": true, "waiting": {"applications": 2, "missions": 1, "cleanups": 0, "logos": 1, "tiktok": 0, "thanks": 0, "late": 1}, "newest": {"applications": "2026-11-05T09:12:44.120Z", "missions": "2026-11-04T17:03:10.511Z", "cleanups": null, "logos": "2026-11-05T10:01:12.004Z", "tiktok": null, "thanks": null, "late": "2026-11-28T00:00:00.000Z"}}`: new applications not decided yet, missions in review, cleanups in PENDING, crew logos under LOGOS TO CHECK and crew TikTok accounts under TIKTOK TO CHECK (of active crews), busy days of thanks (the UTC days, today or yesterday, with 200 or more standing thanks on the site or 100 or more on one receipt; Thanks, under Post links and thanks), funded missions 3 days or more past their day with no cleanup in PENDING (LATE, under Missions), and when the newest of each came in (for thanks that day at 00:00 UTC, for late missions the day the latest of them became late, at 00:00 UTC; null when none waits). Counts and times only, never names. Before migrations 0003, 0004, 0006, 0007 and 0009 the missing tables count as 0, with newest null. The workflow reads a missing `logos`, `tiktok`, `thanks` or `late` count as 0 (its `OPTIONAL` list), so a run between the push and the deploy of the change that added it does not fail; any other missing or bad value still stops the run. Any method other than POST answers 405.

**Your to-do note.** After each run the workflow keeps one open issue in the GitHub repo, labelled `waiting` and titled "Waiting for you on sapu.earth":

- Something waits and no such issue is open: it opens one with the counts and a link to `/admin/`. The issue mentions `@marcus-pousette`, so GitHub emails you.
- Something new comes in: it adds a short comment that mentions you, so you get another email. New means a count went up, or the newest one came in after the newest the last run saw. The second catches a crew that sends a fixed cleanup right after you rejected one: the count stays the same, but it is new.
- Less waits: it updates the issue text, no email.
- Nothing waits: it closes the issue. The next time something waits, a new one opens.

So you hear about a new application, mission, cleanup, crew logo, crew TikTok account, busy day of thanks or late mission at the next run, not at once: usually within a few hours, so far at most about 10 (3.6 hours on average in the first two days). While crews are applying or a funded mission is due, open `/admin/` once a day yourself. The issue keeps the last counts and times in a hidden comment at the end of its text: leave that line if you edit the text. Removing the `waiting` label makes the workflow ignore that issue. The emails depend on your GitHub notification settings (Settings, Notifications: email for participating and @mentions, the default).

Nothing to set up: the workflow starts once it is on `main`, together with the endpoint. If the first run starts while Pages is still deploying, that run fails and the next one works. A failed run (sapu.earth down, an error) gets you an email from GitHub; the next run tries again. If runs keep failing with 403, a Cloudflare security setting is blocking GitHub's servers: a WAF custom rule, Browser Integrity Check or Bot Fight Mode. For a custom rule or Browser Integrity Check, add a custom rule that skips it for `/api/housekeeping`. Bot Fight Mode (Security, Bots) cannot be skipped for one path on the Free plan (skip rules do not reach it), so turn it off; it was off when the workflow was set up. A 429 is the rate limiting rule (step 4, item 5): the workflow waits 10 seconds and tries again, up to 3 times, so it only fails a run when something else on the runner's address keeps going over 100 requests in 10 seconds. The repo is private, so the runs count against your GitHub Actions minutes: 1 minute each, about 240 a month (GitHub Free includes 2,000 a month).

Locally the 10-minute mark is in the Cache API inside the server's `--persist-to` folder. `scripts/test.sh` starts with an empty folder, so the first POST of every test run does the work. Against a `scripts/dev.sh` copy that ran the housekeeping less than 10 minutes ago, `tests/e2e.sh` prints a NOTE instead of checking the cleanup of a loose file.
